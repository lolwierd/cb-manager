Fourteen hidden taxes on an app that promises instant

The Cost
of a Paste.

A ledger of accrued performance costs in a macOS clipboard manager — ordered by what they take, and how often they take it.

14 findings 4 tiers 2 critical ~6h total fix

Prologue

Every clipboard paste is a small contract with the user: I will remember this, and I will not make you wait. CB Manager honours that contract. Recent commits stamped out the two worst freezes — the every-other-open stall and the search-scroll seize — and the app now opens cleanly, pastes cleanly, scrolls cleanly.

What's left is the slow accounting. A clipboard manager is a long-running process: it accrues cost not in single dramatic hangs but in microseconds-per-keystroke, kilobytes-per-screenshot, fsyncs-per-capture. Multiplied by a workday. Multiplied by a month of uptime.

This audit inventories the remaining line items. Two of them — an untuned SQLite and an unbounded duplicate-signature cache — are critical because they get worse the longer the app runs. Four are high because they bite during ordinary use. Eight more are smaller: hygiene, compounding wastes, trivial wins. None of this is a regression. It's the next layer of polish on an app that already works.

II · Tier one

Critical

2 findings · phase 1
Critical

Costs that do not level off.

These two findings are the only ones whose damage increases with uptime. A clipboard manager lives at the login item, often for weeks between restarts. Anything that grows linearly in weeks-of-use earns the top tier automatically.

§01 Critical LocationClipboardDatabase.swift
L. 186–191 Accrual▸ per-event
∞ background Phase1 · biggest win

No WAL, no tuning — every write pays rent.

What

The database opens with SQLite's factory settings: journal_mode = DELETE, synchronous = FULL, no busy timeout, no temp_store override. These are correct, but they are not choices. They are what you get when you don't pick.

Impact

Every INSERT or UPDATE triggers a full fsync. A clipboard capture — which should feel instant — blocks waiting for the disk. Under DELETE journaling there is also no reader/writer concurrency, so background work (OCR results writing back, AI titles resolving, QMD upserts) contends with the pasteboard poll. On pressured storage this is the single largest contributor to write-path latency in the app, and it is invisible to the user except as occasional stickiness.

Default SQLite pragmas optimize for survival at rest. WAL optimizes for latency in flight — and costs you nothing.
Fix

In openDatabase(), immediately after sqlite3_open:

// Safe for a single-writer, multi-reader app DB
sqlite3_exec(db, "PRAGMA journal_mode = WAL;",     nil, nil, nil);
sqlite3_exec(db, "PRAGMA synchronous  = NORMAL;",  nil, nil, nil);
sqlite3_exec(db, "PRAGMA busy_timeout = 5000;",    nil, nil, nil);
sqlite3_exec(db, "PRAGMA temp_store   = MEMORY;",   nil, nil, nil);

WAL also makes reads non-blocking during writes, which directly relieves the contention in §05 and partially subsumes §08.

§02 Critical LocationClipboardStore.swift
L. 241, 773–783 Accrual∞ accumulates Phase1 · biggest win

The duplicate-signature dictionary has no exit.

What

imageDuplicateSignatures: [String: ImageDuplicateSignature] is keyed by image path and populated every time the duplicate check runs. It is only emptied when an entry is explicitly deleted, or when the undo-stack's pending-deletion sweep finds it. Each signature carries head- and tail-byte samples — kilobytes per image, by design.

Impact

For a user who traffics in screenshots — designers, QA, anyone in review — the dictionary grows continuously and never shrinks for the lifetime of the process. A month-long session accrues tens of megabytes of ghost state: signatures for images the user long since forgot about, kept alive solely by this cache. The app's memory footprint looks fine at launch and bloats over uptime. Classic slow leak.

A dictionary is a map, not a cache. It has no notion of "old" and no reason to let go.
Fix

Replace with an NSCache. Set a count limit, a total cost limit, and pass the signature byte-count as the cost on insert. The OS handles LRU eviction automatically under memory pressure.

// ImageDuplicateSignature is a struct; wrap for NSCache.
final class ImageDuplicateSignatureBox: NSObject {
    let value: ImageDuplicateSignature
    init(_ v: ImageDuplicateSignature) { self.value = v }
}

private let imageDuplicateSignatures: NSCache<NSString, ImageDuplicateSignatureBox> = {
    let c = NSCache<NSString, ImageDuplicateSignatureBox>()
    c.countLimit     = 256
    c.totalCostLimit = 32 * 1024 * 1024   // 32 MB
    return c
}()

Update the insert site to pass a cost roughly equal to head.count + tail.count. Cache misses now re-read the sample bytes from disk — which is cheap for 32 KB of file I/O, and exactly what NSCache is designed for.

High

4 findings · phase 2 & 3
High

Felt during ordinary use, at ordinary scale.

These don't grow unbounded, but they make themselves known. A stutter during arrow-key navigation, a hitch when many images scroll past, a slow bootstrap after a long history import — all reliably reproducible on a typical user's week-old history.

§03 High LocationSearchOverlayView.swift
L. 48–52 Accrual▪▪▪ per keystroke Phase2

Linear scan of the filtered list, once per body evaluation.

What

The selectedEntry computed property resolves the currently selected ID by calling entries.first { $0.id == selectedID }. SwiftUI re-evaluates the body on any @Published change — every keystroke, every filter tick, every selection move — and each evaluation runs a fresh O(n) scan.

Impact

Invisible at a hundred entries. Visible at a thousand. The preview pane reads selectedEntry too, so each body evaluation pays the cost twice. Arrow-key nav on a large history becomes stuttery in a way that's maddening because the app looks responsive — the text is ready, the pane just lags the caret.

Fix

Maintain an index dictionary alongside filteredEntries, rebuilt inside recomputeFilteredEntries(). Lookup becomes O(1).

// in ClipboardStore
@Published private(set) var filteredEntries: [ClipboardEntry] = []
private var filteredIndexByID: [ClipboardEntry.ID: Int] = [:]

private func recomputeFilteredEntries() {
    // ... existing work ...
    filteredIndexByID = Dictionary(
        uniqueKeysWithValues: filteredEntries.enumerated().map { ($1.id, $0) }
    )
}

func entry(for id: ClipboardEntry.ID) -> ClipboardEntry? {
    filteredIndexByID[id].map { filteredEntries[$0] }
}

Call store.entry(for: selectedID) from the view. Keep filteredEntries.first as the fallback for "no selection yet." The index is discarded and rebuilt wholesale — no partial-update gymnastics required.

§04 High LocationClipboardDatabase.swift
L. 193–213 Accrual◉ startup
▸ future paths Phase3

One index exists. The schema has three filterable columns.

What

Only idx_clipboard_entries_created_at is declared. The app filters by kind (the pill selector in the overlay) and — by design intention — by source_app. Current kind filtering is done in memory after loadEntries() pulls the whole table, so the absence is invisible today. Any future work that wants to filter server-side, paginate, or delete-by-kind will hit a full table scan.

Impact

Not felt in the current code path. Felt immediately the first time someone writes DELETE FROM clipboard_entries WHERE kind = 'image' or migrates to paginated loading. This finding is ranked High because the indexes cost almost nothing to add and unblock a class of future changes that are otherwise embarrassing to get wrong under load.

Fix 
CREATE INDEX IF NOT EXISTS idx_clipboard_entries_kind
    ON clipboard_entries(kind);

CREATE INDEX IF NOT EXISTS idx_clipboard_entries_source_app
    ON clipboard_entries(source_app);

Add to createSchema(). SQLite will build both in one pass. For a 5,000-row table the one-time cost is in milliseconds, after which every subsequent filter path is O(log n) instead of O(n).

§05 High LocationQMDSearchEngine.swift
writeDocument() Accrual◉ bootstrap
▸ every upsert Phase3

Every upsert serializes and overwrites the full markdown.

What

writeDocument() re-renders the entry's complete markdown representation on every upsert, then writes it to disk. An entry is upserted at least three times in normal operation: once on capture, again when OCR resolves, and again when the AI title lands. On bootstrap it's called once per entry in the existing history, back to back.

Impact

Slow first-index after a fresh install or after importing a history dump — the user sees an app that "feels unresponsive for a while" on launch. During normal use there's a constant trickle of markdown writes as OCR and AI titles resolve asynchronously. None of it is individually slow; all of it is individually unnecessary.

If three systems each rewrite the same document in the same second, the disk doesn't care who's right — it just writes three times.
Fix

Coalesce per-entry writes with a short debounce, and avoid the full re-serialization when only one field changed.

private var writeTasks: [String: Task<Void, Never>] = [:]

func upsert(_ entry: ClipboardEntry) async {
    await ensureCollection()
    writeTasks[entry.id]?.cancel()
    writeTasks[entry.id] = Task {
        try? await Task.sleep(for: .milliseconds(200))
        guard !Task.isCancelled else { return }
        writeDocument(for: entry)
        scheduleUpdate()
    }
}

For bootstrap, dispatch the N writes on a detached utility task with bounded concurrency (a semaphore of 4–8 is plenty). Longer term: consider whether N markdown files is even the right shape — a single JSONL index could replace them all with one append per upsert.

§06 High LocationThumbnailCache.swift
L. 14–22 Accrual▪▪▪ per scroll tick Phase2

One NSLock, two responsibilities, four contenders.

What

A single NSLock guards both the NSCache read/write path and the in-flight load tracking dictionaries. NSCache is already thread-safe internally — the extra lock is double-guarding the hot path.

Impact

Fast scrolling through a window dense with image entries wakes multiple threads: SwiftUI's rendering threads, thumbnail decoders, the main thread requesting cached previews. They all pay a trip through the same lock. Contention shows up as micro-stalls during scroll — the kind of thing you can't quite screenshot but you can feel.

Fix

Split the responsibilities. Let NSCache handle its own reads and writes directly (no lock). Use os_unfair_lock — cheaper than NSLock — for the in-flight dictionaries only.

private var inFlightLock = os_unfair_lock_s()
private var inFlightLoads: [NSString: DispatchGroup] = [:]

private func withInFlight<T>(_ body: () -> T) -> T {
    os_unfair_lock_lock(&inFlightLock)
    defer { os_unfair_lock_unlock(&inFlightLock) }
    return body()
}

// cache reads/writes: no lock needed, NSCache is thread-safe.
// only dict access goes through withInFlight { … }
IV · Tier three

Medium

Medium

Small cuts on the common path.

Each is individually trivial; collectively they shave measurable latency off the hottest loops. Order the checks from cheap to expensive, batch the obvious, move the blocking work off the poll thread.

§07 Medium LocationClipboardStore.swift
L. 1022+ Accrual▸ per-event Phase3

classify() calls URL() on strings that are obviously not URLs.

What

Every text capture runs URL(string: trimmed) as part of classification, even for plain prose or code. URL's initializer is not free — it validates scheme, host, percent-encoding, the whole RFC 3986 tree — and it does this work even when the string has no chance of being a URL.

Impact

Per-paste overhead, small but unavoidable. For a user who copies code snippets and prose all day, it's a steady drip against a path that should be the cheapest thing in the app.

Fix

Guard the URL() call behind a cheap prefix check. Order the whole classifier from cheapest to most expensive probe — file paths and code-hints first (simple hasPrefix / contains), URL parsing last and only when the input plausibly could be one.

private func classify(_ text: String) -> ClipboardEntry.Kind {
    let trimmed = text.trimmingCharacters(in: .whitespacesAndNewlines)

    // Cheap checks first…
    if trimmed.hasPrefix("/") || trimmed.hasPrefix("~/") { return .path }
    if looksLikeCode(trimmed) { return .code }

    // URL parsing only if it could conceivably succeed.
    let lower = trimmed.lowercased()
    if lower.hasPrefix("http://") || lower.hasPrefix("https://") {
        if let url = URL(string: trimmed),
           let scheme = url.scheme?.lowercased(),
           ["http", "https"].contains(scheme) {
            return .link
        }
    }
    return .text
}
§08 Medium LocationClipboardDatabase.swift
L. 25–69 Accrual◉ startup Phase4

loadEntries runs outside a transaction.

What

loadEntries() issues a single SELECT, so it's auto-committed. Without an explicit BEGIN DEFERRED, SQLite still takes a shared read lock and releases it around the statement — minor overhead per call.

Impact

Startup contribution only, small. Worth mentioning because it's trivial to fix, but mostly because enabling WAL in §01 will absorb most of the benefit automatically — concurrent reads don't wait on anything once WAL is on.

Fix

Either wrap in BEGIN DEFERRED; COMMIT;, or consider this fix-by-dependency: land §01 and reassess whether this one still shows up in traces.

§09 Medium LocationSearchOverlayView.swift
L. 423–469 Accrual▪▪▪ per keystroke Phase3

Full regrouping on every filter version bump.

What

scheduleVisibleEntriesRebuild rebuilds groupedEntries and flattenedEntryIDs on any filteredEntriesVersion change, even when the visible-window limit and top-N identities are unchanged.

Impact

Visible as a brief lag while typing a refining search query — narrowing 500 results to 100 still rebuilds everything. Not a freeze, just a hitch. The recent eliminate-search-freezes commit got this below the pain threshold; the remaining work is pushing it below the perception threshold.

Fix

Short-circuit the rebuild when the computed effective limit equals the previous visibleEntryLimit and the entry identities at positions 0..<limit haven't changed. An alternative (more work, better result): maintain grouping incrementally as entries enter and leave the window.

§10 Medium LocationClipboardStore.swift
L. 1006–1020 Accrual▸ per image paste Phase2

persistImage encodes and writes PNG inline on the poll thread.

What

On an image capture, persistImage() runs NSImage → TIFF → NSBitmapImageRep → PNG encode → disk write, all synchronously on the pasteboard poll thread inside pollPasteboard().

Impact

One image, no problem. A burst — dragging out a sequence of screenshots, copying frames from a contact-sheet — serializes on the encode loop. Each paste blocks the next poll tick, which delays the next capture, which compounds the queue.

Fix

Move encode + write to a detached utility task. The entry can be inserted immediately with the pending image path; the file appears shortly after. If the overlay opens in the brief window where the file doesn't exist yet, the thumbnail loader already handles missing files gracefully.

private func persistImage(_ image: NSImage, id: String) -> String? {
    let destination = imageDirectory
        .appendingPathComponent("\(id).png")

    Task.detached(priority: .utility) {
        guard let tiff = image.tiffRepresentation,
              let bitmap = NSBitmapImageRep(data: tiff),
              let png = bitmap.representation(using: .png, properties: [:])
        else { return }
        try? png.write(to: destination)
    }
    return destination.path
}

For bulk-paste workflows, consider a serial background queue with bounded depth so that a hundred rapid captures don't fan out a hundred concurrent encodes.

Low

4 findings · phase 4
Low

Hygiene. Microseconds. Leave-them-better-than-you-found-them.

Nothing on this tier will ever appear in a bug report. It's here because these are the edits you make while you're in the file for a real reason — and because doc hygiene catches a code smell before it grows.

§11 Low LocationClipboardSearch.swift Accrual▪▪▪ per keystroke Phase4

Convenience overload re-tokenizes the query.

What

Public fuzzyScore(entry:, query:) re-splits the query string internally; the pre-tokenized overload exists but some callers take the string path. The cost is microseconds, but it's zero-reason microseconds.

Fix

Tokenize once at the top of rank() and call the token-array overload everywhere. Consider marking the string overload @available(*, deprecated) to steer callers.

§12 Low LocationQMDSearchEngine.swift
ImageTitleGenerator.swift Accrual◉ first launch Phase4

Two actors, two login shells, one PATH.

What

Both actors independently spawn a login shell to resolve $PATH and locate their respective binaries. The code is near-duplicated; the -ilc vs -lc difference is intentional (QMD needs interactive PATH init for nvm/fnm resolution).

Fix

Extract a shared PATHResolver utility with memoized results per shell-mode, so the shell spawn runs once per process, not twice.

enum PATHResolver {
    static func resolved(interactive: Bool = false) async -> String { /*…*/ }
    static func findBinary(_ name: String, in path: String) -> String? { /*…*/ }
}
§13 Low LocationSearchOverlayView.swift
L. 759–768 Accrual▪▪▪ per selection Phase4

inlineMetadataStats recomputes counts on every preview update.

What

Character count and whitespace-split word count are computed every time the selection changes, on the previewed entry's content prefix. Trivial for short entries; not quite trivial when the selection rapidly oscillates across long entries near the metadata scan limit.

Fix

Cache characterCount and wordCount inside SelectedEntryDetails. A return-visit to a previously-previewed entry becomes free.

§14 Low LocationClipboardStore.swift
L. 146–158 Accrual◉ on init
▸ on refresh Phase4

buildSearchableText allocates an array to join six strings.

What

An intermediate array → .joined(separator:) → .lowercased() chain per entry init. Allocation overhead is small; allocation count is larger than it needs to be.

Fix

Only worth changing if profiling says so. A mutable String with append interpolation would halve the allocations. This finding exists mainly to flag that the code as written costs more than its readability gain demands — revisit when you're next in the file.

What this audit is not

Three corrections to what a first-pass grep would have suggested.

  1. The polling Timer in startMonitoring does use [weak self]. There is no retain cycle. Invalidating the timer in deinit is reasonable hygiene but not a fix for anything that bleeds.
  2. indexOfDuplicate caches the new path's signature on first computation via imageDuplicateSignatures[path]. An earlier read of this code suggested the new-path signature was recomputed on every iteration; it isn't. The real problem with that dictionary is that it never shrinks — see §02.
  3. Recent commits (75115e0 and dd710da) fixed the two freezes that motivated the recent releases. This audit is explicitly not about regressions. It's about the costs that remain after the regressions are already gone.
